## Plan-level decisions

**D-54 · Planet identity is validated before statement content.**
`generateSigil` currently checks statement presence, planet presence, options,
then normalizes and throws `E_EMPTY_SEQUENCE`, and only then calls `gridSize` —
which is what raises `E_UNKNOWN_PLANET`. So a call that is wrong in both ways
reports only the content failure. The ordering flips so that identity of the
target (which planet) is settled before the quality of the input (does the
statement survive normalization) is judged. This makes the comment already sitting
above the `gridSize` call — that it throws "before any further work is done" —
true, where today it is not.

The observable change is narrow and worth naming: an input that is BOTH an unknown
planet AND an empty sequence moves from `E_EMPTY_SEQUENCE` / exit 3 to
`E_UNKNOWN_PLANET` / exit 2. Verified during planning that no existing test
asserts that combination. Rated reversible — the reversal is moving one statement
back.

**D-55 · The five `E_*` constants join the public surface, and the CLI's exit map is rekeyed to them.**
Re-exporting the constants alone would close only half of what the audit recorded.
The stated problem is that `bin/sigil-spinner.js` "hardcodes them as object keys
with no drift protection if a code is renamed" — so the CLI's `EXIT_CODES` map is
rekeyed to computed keys built from the imported constants. Renaming a code in
`src/errors.js` then either propagates or fails loudly at import, instead of
silently leaving an exit-status entry pointing at a code that no longer exists.
`E_CLI_USAGE` and `E_CLI_STDIN` stay out of that map and out of `src/errors.js`
entirely — they are CLI-local by decision from plan 02-04 (INT-04), and the
library remains the sole owner of domain error identity.

**D-56 · The SUMMARY backfill transcribes `02-VERIFICATION.md`; it does not re-derive.**
The correct plan→requirement mapping is already authoritative in
`02-VERIFICATION.md`'s Requirements Coverage table and was inverted once, during
research. Re-deriving it from the four PLAN/SUMMARY files risks producing a
different and less accurate mapping than the one the milestone audit already
accepted.

**Reversibility:** every task in this plan is reversible — a moved statement, an
added export line, and four frontmatter keys. Nothing is one-way or costly, so no
`checkpoint:decision` is inserted.

### Verified non-issues (2) — closed on evidence, not deferred

**Phase 3 WR-02 · `-0` serialization unguarded in `formatCoord`/`roundGeometry`.**
Live-verified during research: `JSON.stringify(-0)` returns `"0"`, `String(-0)`
returns `"0"`, and template interpolation of `-0` returns `"0"`. Both paths this
code actually uses — `formatCoord`'s `String(n)` and `json.js`'s `JSON.stringify`
of `cells[].x`/`cells[].y` — therefore already collapse `-0` to `"0"` with no
guard. It could only matter to a consumer calling `Object.is(x, -0)` on the
pre-stringification numeric value, which no code in this repository does. The
audit itself recorded zero `-0` occurrences across all 14 curve-mode snapshots.
No fix is needed; a guard would be dead code.

**Phase 1 WR-04 · Raw `TypeError` from `gridSize`/`kameaGrid` on a partial kamea set.**
Unreachable. `agrippa` is the only registered kamea set and it is complete for all
seven classical planets, and `src/data/kamea.js` states that no other module in
the repository may contain a kamea grid literal. The failure requires registering
a second, incomplete set — an act that does not exist in the codebase and cannot
occur without a deliberate future change that would itself carry the guard. Adding
the guard now would test a state the type system and the data layer's own
invariant already prevent. If a second kamea set is ever added, that change must
carry a `SigilError(E_UNKNOWN_PLANET)` guard on both resolvers — recorded here as
the trigger condition.
