## Gap 2 direction — decided, with rationale

The verifier offered two directions: extend `TRANSLITERATION_MAP`, or narrow the README's general claim. **This plan does both, and treats "extend the table" as the primary fix.** Recording the reasoning here so it is a cited line item rather than an executor's coin flip.

**Why extend rather than only narrow.** D-23's stated scope is "Non-decomposable Latin letters use a small explicit transliteration map." The *category* D-23 names is precisely "Latin letters NFD cannot resolve" — and Ł, Đ, Ħ, Ŧ are squarely inside that category. The six entries were an enumeration of what came to mind during discussion, not a deliberate exclusion of stroke letters; nothing in 02-CONTEXT.md scopes them out. Meanwhile D-24's stated scope is "Non-Latin script letters (Greek, Cyrillic, Hebrew, CJK, …)" — which is the rule currently *catching* the stroke letters, and which does not cover them by its own wording. So today these letters are handled by a rule whose text excludes them, which is the actual defect. Narrowing the README alone would document an inconsistency rather than remove one, and CONS-04's criterion asks for a rule "observed applied consistently in output" — a documented inconsistency does not satisfy that.

**Why the whole stroke/bar class, not just the eight reported letters.** Adding only Ł/ł/Đ/đ/Ħ/ħ/Ŧ/ŧ closes the reproduced case and leaves the class open — Ƶ, Ǥ, Ɇ, Ⱥ and the rest would fail identically the next time anyone looked. The class has a mechanical, non-judgmental definition: a Latin letter whose Unicode name identifies a single A-Z base letter plus a stroke or bar overlay. Derived from the Unicode character database against the current NFD behavior, that class is exactly **72 characters**, and it is case-complete (every member's single-character case partner is also a member). The table therefore goes from 12 keys to 84.

**Why not go further.** 153 Latin letters remain that NFD cannot resolve. The remainder are digraphs (`Ĳ`, `Ǆ`, `Ǉ`, `Ǌ`, `Ǳ`, `ȸ`), reversed/turned/rotated letters (`Ǝ`, `Ə`, `ǝ`, `ƍ`, `Ʌ`), and hooked/tailed phonetic letters (`Ɓ`, `Ƈ`, `Ɗ`, `Ƒ`, `Ɠ`, `Ƙ`, `Ƥ`, `Ƭ`, `Ƴ`, …). For those the base letter is genuinely ambiguous or absent, so a fold would be an invention rather than a transliteration. They stay struck as `non-letter` — **as a decision, written down in the README with its reason**, not as an unbuilt remainder.

**Reversibility: `costly`.** Determinism means this changes output for any statement containing a stroke letter — previously an `E_EMPTY_SEQUENCE` or a dropped character, now a kept consonant. Reverting would break any sigil already generated from such a statement. It is not one-way: no data migration, no external contract destroyed, no snapshot rewritten (verified — zero stroke letters appear anywhere under `test/` or `src/` today). Task 2 gates it on a `checkpoint:decision` anyway, because expanding a table the user locked at six entries to eighty-four exceeds D-23's own word "small" and is a decision amendment, not an implementation detail.
