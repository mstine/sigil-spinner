  <context>Removing or repointing a published `exports` subpath breaks every consumer importing it — this is a `one-way` door once `1.1.0` reaches the registry, and the phase's whole packaging story hangs off it.

D-84's shape is `{ ".": "./src/index.js", "./element": "./src/element/sigil-spinner-element.js", "./package.json": "./package.json" }`, with four deliberate non-choices inside it:
- **No `browser` condition on `.`** — there is no divergence to encode; a condition pointing at the same file reads as "there must be a difference" to a future maintainer who then goes looking for one.
- **No `browser` condition on `./element`, and no `node` condition excluding it** — conditions exist to pick between *interchangeable* implementations, and there is no Node-compatible alternative custom element to fall back to. The correct signal is documentation (D-97), not a condition that lies about having an alternative.
- **No wildcard `"./*"`** — it would silently promote every internal module to public API, destroying the single-entry-point discipline `src/index.js`'s own header states.
- **`main`, `bin`, and `files` untouched** — `files` already covers `src/element/` through its `src` entry.

The `./package.json` entry is conventional and cheap: a populated `exports` map otherwise blocks ALL unlisted subpaths, the package's own manifest included, which breaks tooling that reasonably expects to read it.

Note the interaction with D-98: nothing is published in this phase, so the door is not yet walked through irrevocably — but the shape locked here is the shape the milestone-close publish will ship.</context>
