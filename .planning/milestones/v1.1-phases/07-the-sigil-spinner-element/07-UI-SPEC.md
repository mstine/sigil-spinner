# Phase 7 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scoping note (read first).** This is not a greenfield UI phase. The sigil SVG's own look — its
seven semantic classes, its 15 `--sigil-*` custom properties, its geometry — shipped in v1.0/v1.1
Phase 3, is byte-pinned by 48 snapshots, and is a published contract this phase must not touch
(README.md § CSS Custom Properties, lines 163–260; `03-UI-SPEC.md`). This document treats that
surface as **locked and referenced**, never redeclared or reopened. What this phase actually adds
that needs a design contract is genuinely new:

1. **The `<sigil-spinner>` custom element's observable states** — inert/empty, rendered, error,
   re-render, multi-instance (D-91–D-93) — a state-coverage contract the element didn't have before.
2. **`examples/element.html`** — a real, repo-only HTML page with real layout, real typography, real
   chrome color (D-95). This is the phase's one genuinely new page-level visual artifact, and it is
   load-bearing: ROADMAP success criterion 1 requires a human to look at it and confirm a visibly
   correct sigil.
3. **The host element's layout/sizing contract** — a custom element has no default `display` beyond
   the platform's `inline` fallback, and the inner SVG has a fixed viewBox but no `width`/`height`.
   Getting this wrong reproduces the exact "renders nothing visible while looking correctly wired"
   failure class the v1.0 postmortem (Pitfall 8) already burned this project on once.
4. **Copywriting for the new failure/absence states and the README's new element section** (D-97).

Everywhere this document says "locked, referenced" it means: do not redesign it, do not
re-derive it, cite the existing source instead.

### Attribute Contract (the element's component API — locked in CONTEXT, restated here as the design-facing inventory)

| Attribute | Maps to | Type / Semantics | Design-relevant behavior |
|-----------|---------|-------------------|---------------------------|
| `statement` | `generateSigil(statement, …)` | string, required | Absent → inert/empty (D-91) |
| `planet` | target planet | string, required, one of the seven classical planets | Absent → inert/empty; invalid value → `SigilError` (D-92) |
| `curve` | `options.curve` | boolean, **presence-based** (D-81) | `curve="false"` still enables curves — the footgun must be stated explicitly in the README, never smoothed over |
| `glyph` | `options.glyph` | boolean, presence-based | Same presence semantics as `curve` |
| `id-prefix` | `options.idPrefix` | string, optional | Kebab-case attribute → camelCase option at the call boundary (D-79); XML-escaped by the library, not the element |
| `show-title` | `options.title` | boolean, presence-based | **The one exception to the drop-the-dashes rule** (D-80) — `title` is the global HTML tooltip attribute and cannot be reused. README must state this exception in as many words, not just imply it from the name |

No other attribute exists. `--json`/`--output` (CLI-only transport concerns) have no element analog by design.

### Host Element Sizing Contract

**This is the single most likely source of a "technically correct, visibly nothing" defect in this
phase — the same failure class as the v1.0 lesson, one layer deeper.** A custom element with no
author stylesheet rule computes to `display: inline` (the CSS/UA default for any element the page
hasn't styled, custom elements included — no default stylesheet is attached because D-82 forbids a
shadow root, and this phase adds no global stylesheet of its own). The inner `<svg>` carries a fixed
`viewBox="0 0 100 100"` and **no `width`/`height` attributes** (locked, Phase 1). Combined, an
unstyled, populated `<sigil-spinner>` sitting in ordinary inline flow with no sizing CSS is not
guaranteed to occupy the square area a reader expects — this must be closed by a documented CSS
recipe, not left to be discovered.

**Locked recipe — the README's element section (D-97) and `examples/element.html` (D-95) must both
carry this, verbatim in spirit:**

```css
sigil-spinner {
  display: inline-block;
}
```

That one line is the floor every embedder needs regardless of final size. For a typical
single-sigil embed at a fixed, square presentation (matches the fixed 100×100 viewBox aspect
ratio exactly — no distortion):

```css
sigil-spinner {
  display: inline-block;
  width: 240px;
  aspect-ratio: 1 / 1;
}
```

`240px` is the demo page's own default card size (a multiple of 8, consistent with the Spacing
Scale below) — not a library default, not enforced anywhere, purely a documentation/example
convention. Consumers choose their own width; `aspect-ratio: 1 / 1` is the load-bearing half of the
recipe, since it is what keeps the square viewBox from stretching.

**Inert-state visual contract (D-91, restated as a design fact):** an inert instance (missing
`statement` or `planet`) renders zero content into its light-DOM children. Styled with the recipe
above, it collapses to a `0 × 0` content box inside a sized-but-empty host — **this is the correct,
expected signal that required attributes are missing, not a rendering bug.** The README's attribute
table documents this next to the empty-state copy (see Copywriting Contract).

## Spacing Scale

Declared values (must be multiples of 4) — **scoped to `examples/element.html`'s own page chrome
only.** The sigil's internal geometry stays locked at Phase 3's fraction-of-`cellSize` scale
(`03-UI-SPEC.md` § Geometry Constants) and is not redeclared here.

| Token | Value | Usage on `examples/element.html` |
|-------|-------|-----------------------------------|
| xs | 4px | Gap between a demo card's caption text and its "mechanism" label |
| sm | 8px | Gap between a rendered `sigil-spinner` and its caption |
| md | 16px | Demo-card internal padding; gap between attribute-table rows in the on-page copy |
| lg | 24px | Padding around each demo section (e.g. "Custom Property Overrides," "Class Selector Overrides") |
| xl | 32px | Grid `gap` between sigil gallery cards |
| 2xl | 48px | Vertical gap between major page sections (title → gallery, gallery → live-control demo) |
| 3xl | 64px | Page top/bottom margin |

Exceptions:
- The sigil's own geometry (locked, Phase 3, fraction-of-`cellSize`, not this scale) — referenced, never redeclared.
- The host element's `240px` default card width (Host Element Sizing Contract, above) is a
  component-sizing token, not a spacing token, and does not need to be a member of this scale — it
  happens to be a multiple of 8 for consistency, not because the scale requires it.

## Typography

**Two separate, non-overlapping typography contexts this phase touches — keep them separate in
planning and code review.**

1. **`examples/element.html` page chrome** (genuinely new this phase):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.2 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

Two weights total (400, 600) across four sizes (16/14/20/28) — hierarchy is carried by size
progression, not weight variation; Display gets no heavier a weight than Label/Heading, only a
larger size.

Font: `system-ui, sans-serif` — no web font, no `@font-face`, no build step. This is consistent
with the milestone's zero-dependency/no-build-step constraint and with D-37's standing refusal to
embed fonts; it is plain, hand-authored CSS text, never a network font load.

2. **The sigil's own two text layers** (`.sigil-grid-number`, `.sigil-glyph`) — **locked at Phase 3,
   not redeclared.** Both default to `sans-serif` via `--sigil-grid-number-font` /
   `--sigil-glyph-font`, sized as a fraction of `cellSize` per planet (`03-UI-SPEC.md` § Typography).
   `examples/element.html`'s own `system-ui` chrome font must never be applied to these — they are
   the page-author's override surface, not the page's global font stack, and conflating the two
   would misrepresent the library's actual (zero-opinion) default to anyone reading the example as
   documentation.

## Color

**Two separate color surfaces — do not conflate them.**

### 1. `examples/element.html` page chrome (genuinely new this phase)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` | Page background |
| Secondary (30%) | `#f4f4f5` | Demo-card and section backgrounds — visually separates each mechanism demo from the page background |
| Accent (10%) | `#2563eb` | Reserved for exactly: the live attribute-mutation control's `<label>` text, its focus outline, and a small "Live" badge next to it |
| Destructive | N/A | No destructive actions exist anywhere on this page |

Accent reserved for: **the live control only** (label, focus ring, "Live" badge). Never applied to
any sigil paint property — the sigil's own `currentColor` inheritance (locked, Phase 3 D-40) must
render at whatever the page's default text color is, unstyled, so the example honestly represents
the library's real zero-opinion default rather than the demo page's own branding.

### 2. Theming-mechanism demonstration palette (D-95 — "both mechanisms exercised side by side and
visibly distinguishable")

This is the one place this phase assigns color *to the sigils themselves*, and only because D-95
explicitly requires the two theming mechanisms to be visually distinguishable from each other, not
because the library has an opinion about sigil color:

| Demo sigil | Mechanism | CSS | Resulting color |
|------------|-----------|-----|------------------|
| Default (no override) | — | none — unstyled | `currentColor` (page's default text color) |
| Custom-property override | `--sigil-*` | `--sigil-stroke: #0d9488;` set on the host or an ancestor | Teal |
| Class-selector override | semantic class | `.sigil-path { stroke: #ea580c; stroke-dasharray: 4 2; }` | Orange, dashed |

Teal (custom property) vs. orange-dashed (class selector) is deliberately maximally distinguishable
— different hue *and* a stroke-pattern difference — so a human glancing at the rendered page (the
success-criterion-1 check) can immediately tell the two mechanisms apart without reading the page's
source.

### 3. Error-state CSS hook (D-92 — "is there a documented CSS hook a page can use to style the error
state," resolved here)

`data-sigil-error="<code>"` is reflected on the host on a thrown `SigilError` and removed on the
next successful render (locked, D-92). The library itself ships **no default visual style** for
this state — D-92 is explicit that the element "has no visual vocabulary of its own." The design
contract this phase owns is the **hook name and a documented example recipe**, not a shipped
default:

```css
/* Documentation example only — never shipped as library CSS */
sigil-spinner[data-sigil-error] {
  outline: 2px dashed #dc2626;
  outline-offset: 4px;
}
```

**Recommendation (not a D-95 requirement — flagged so it is not confused with a locked decision):**
`examples/element.html` should include one intentionally-erroring instance (e.g. an invalid
`planet` value) styled with this recipe, so the human success-criterion-1 check also confirms the
error contract visually, not only the happy path. This is Claude's discretion to include or cut at
plan time — the CSS hook name and recipe above are the part of this that is locked by this
document.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | N/A — no app-level action exists. Real analog: the live attribute-mutation control's label, `<label for="live-planet">Change planet</label>` next to a `<select id="live-planet">` whose seven `<option>` values are the classical planet names (Saturn, Jupiter, Mars, Sun, Venus, Mercury, Moon) — its `change` event sets the target `sigil-spinner`'s `planet` attribute, demonstrating WRAP-03's re-render contract |
| Empty state heading | N/A — no list/collection empty state exists |
| Empty state body | N/A as app copy. Real analog — README sentence (D-97, next to the attribute table): *"A `<sigil-spinner>` missing `statement` or `planet` renders nothing and throws nothing. This is the expected inert state, not an error — set both attributes to render."* |
| Error state | Real analog, two parts. **Console:** `console.error('<sigil-spinner> failed to render:', error)` where `error` is the full, unmodified `SigilError` object (its `.message`, `.code`, `.details` stay intact — no re-wrapping, no re-summarizing). **README** (D-97): *"A thrown error clears the element, logs the full error to the console, and reflects `data-sigil-error="<code>"` on the host element — style it with `sigil-spinner[data-sigil-error] { … }` if you want a visible signal on the page."* |
| Destructive confirmation | N/A — no destructive actions exist in this phase |

**D-80 naming-exception copy (required README content, stated once so the plan does not have to
re-derive the wording):** the README's attribute table must call out, in prose, that `show-title` is
the sole exception to the "drop the `--`, keep the dashes" attribute-naming convention, and name the
reason (`title` is a global HTML attribute that renders a browser tooltip and would collide with
`options.title`'s unrelated meaning) — not merely list `show-title` alongside the others as if the
naming pattern were uniform.

**D-81 presence-semantics footgun copy (required README content):** the README must state, in these
terms or clearer ones, that `curve="false"` still enables curves, and that the only way to disable a
boolean attribute is to remove it — `<sigil-spinner curve="false">` and `<sigil-spinner curve>` are
identical. This is not optional disclosure; D-81 requires it stated explicitly, not implied by a
generic "HTML boolean attribute" cross-reference.

### Resolved — explicit

Each lifts into `must_haves.truths` as a plain string. Every one is a checkable assertion the
browser test (D-94) or a source assertion can prove.

| # | Category | Element(s) | Truth |
|---|----------|-----------|-------|
| 1 | empty | E1 | A `<sigil-spinner>` carrying only one of `statement`/`planet` (or neither) has zero element children, emits no thrown error, and carries no `data-sigil-error` attribute — the inert state of D-91. Setting the missing attribute renders it, from the same instance, with no page reload. |
| 2 | error | E1 | Setting `planet` to an unknown value clears the element to zero element children and reflects `data-sigil-error="E_UNKNOWN_PLANET"` on the host; setting `planet` back to a valid one removes the attribute and restores an `<svg>` child (D-92's full round trip, not just the error leg). |
| 3 | populated | E1 | A connected `<sigil-spinner>` with valid `statement` and `planet` has `innerHTML` byte-identical to `generateSigil(statement, planet, options).svg` for the same inputs — the pure-pass-through claim of D-85/D-86 stated as an equality rather than as "an SVG is present". |
| 4 | long-text | E1 | With a `statement` far longer than any test fixture (≥500 characters), the rendered `<svg>` still carries `viewBox="0 0 100 100"` and its `.sigil-path` still has a non-degenerate bounding box — sigil geometry is bounded by kamea order, not statement length (locked, Phase 1–3), so more kept letters densify the path inside the same fixed viewBox rather than overflowing it. |
| 5 | error | E2 | Navigating to the served `examples/element.html` yields at least one rendered `.sigil-path` — which fails loudly if the module never loaded. This is the assertion that catches the module-load failure class RESEARCH.md identified: the static server MUST send `Content-Type: text/javascript` or Chromium's strict MIME enforcement silently rejects the module and every `<sigil-spinner>` on the page stays inert with no console error of its own. |
| 6 | zero-one-many | E2 | Several co-rendered `<sigil-spinner>` elements on one page each contain exactly one `<svg>`, and the count of `id` attributes anywhere within their rendered subtrees is zero (D-93 — id-free by construction, not by generated uniqueness). Re-rendering one instance leaves the others' content unchanged. |

| # | Category | Element(s) | statement | verification |
|---|----------|-----------|-----------|---------------|

| B2 | populated | E2 | The three theming demonstration sigils — default/unstyled, custom-property teal, class-selector orange-dashed — are simultaneously legible and visibly distinguishable from one another on the rendered page. | B3 | overflow | E2 | The gallery's card grid (`240px` cards, `32px` gap) wraps and reflows at a narrow viewport without any card's sigil being clipped or its caption overlapping a neighbour — a plain CSS layout claim on a repo-only demo page, verified by looking. | backstop |

|---|----------|-----------|--------|
| 1 | loading | E1 | `generateSigil` is synchronous and pure and the render is a synchronous whole-content replacement (D-89) — there is no I/O, no async boundary, and therefore no in-flight window for a loading state to occupy. |
| 2 | empty | E2 | The gallery is hand-authored fixed markup decided at implementation time — it has no runtime "zero sigils" state; it is populated the moment the page is authored. |
