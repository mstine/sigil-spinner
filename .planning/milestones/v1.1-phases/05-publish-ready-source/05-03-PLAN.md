## Planner decisions in the discretion areas

CONTEXT.md left INT-05's flag shape and INT-06's id derivation to planning. These are the calls, with rationale, so the executor implements a decision rather than re-deriving one.

**INT-05 flag shape — presence-only boolean, no negated form.** `title` becomes a seventh `parseArgs` option with the same shape `--glyph` and `--curve` already use: boolean, defaulting to false. There is no `--no-title`. Two independent reasons: the library's absent-option default for a boolean is already false, so omitting the flag *is* the negation and there is no affordance gap; and `parseArgs`'s only negation mechanism, `allowNegative`, landed in Node 22.4, above this project's committed `>=20.0.0` engines floor — it would work on every developer machine and silently fail for a consumer on the documented floor. Hand-rolling token reprocessing to substitute for it would be a second inconsistency with the zero-cleverness `parseArgs` convention. — Reversibility: costly. The flag name is public CLI surface from v1.0.0, but the name is *determined* by INT-05's parity requirement rather than chosen from alternatives, so there is no door to deliberate over.

**INT-06 scope — role and aria only when a title and a non-empty id prefix are both present.** This is exactly INT-06's own wording and criterion 3's own wording. The title-only case stays a bare `<title>` with no synthesized id, because D-44 makes `idPrefix` the sole route to an emitted id and Phase 5 exists to avoid shipping public surface nobody asked for right before an irreversible publish. Consequence, deliberate and documented rather than discovered: a titled sigil with no id prefix keeps whatever accessible-name support the viewer's browser gives a bare `<title>`, which the research notes is inconsistent. README must state that supplying an id prefix is what guarantees the accessible name.

**INT-06 id derivation — the escaped id prefix plus a `-title` suffix.** Readable, deterministic, and collision-safe in exactly the way the root id already is: two sigils on one page with distinct prefixes get distinct title ids for free. `escapeXml` is applied to `idPrefix` **once**, and the escaped value feeds both the root `id` attribute and the title `id` attribute. Escaping once and reusing is both better code and the reason `test/render/svg.test.js`'s existing assertion that `escapeXml` is invoked at exactly two call sites in the renderer stays green — that assertion is a real trap and hoisting is what avoids it. — Reversibility: costly. The suffix ships in emitted bytes from v1.0.0, so changing it later moves any consumer's pinned snapshot; it breaks no consumer contract, because the reference is emitted and consumed entirely within the artifact.

**Attribute position — after the existing conditional id.** The renderer already interpolates the root `id` after the `class` attribute specifically so the default byte sequence stays untouched when `idPrefix` is absent. The new ARIA attributes follow the same discipline and are interpolated after it, so every existing output byte sequence is preserved.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI argv → library | The intention statement and the id prefix are untrusted input crossing from the command line into the library. |
| library → SVG markup embedded in a consumer's page | Every emitted attribute value lands inside markup that a page will parse. An unescaped value breaks out of its attribute and becomes markup. |
| library → assistive technology | The role and the ARIA reference are claims made to a user's screen reader about what the graphic is and what it is called. |
