# Milestone v1.1 Audit — Sigil Spinner

**Audited:** 2026-08-09
**Status:** `tech_debt` — all 14 requirements satisfied, no critical blockers, one scheduled milestone-close action outstanding, 17 deferred items
**Milestone goal:** Get Sigil Spinner out of the repo — published, discoverable by any Claude Code session, and embeddable as a custom element — without breaking the zero-runtime-dependency guarantee.

## Verdict

Two of the three legs of the milestone goal are demonstrably true right now against live infrastructure. The package is published, attested, and installable from a clean machine with zero transitive dependencies. The skill is installed, byte-identical to its repo-canonical source, and a cold Claude Code session was observed routing to it unprompted and choosing a planet with stated reasoning.

The third leg — *embeddable as a custom element* — is built, verified 28/28 in a real browser, and confirmed by a human looking at a rendered page. It is not, however, out of the repo. The published `1.0.0` (`gitHead c360ba4`) predates the commit that added the `./element` subpath, so npm serves neither the element file nor its export. Phase 7 scoped this deliberately: D-98 states the phase does not publish and names publishing `1.1.0` "a milestone-close action." That action is what this audit hands to the next step — it is a scheduled item, not a defect, and no requirement text is violated by its absence.

Status is `tech_debt` rather than `passed` because seventeen non-critical items are confirmed still open, and because one of them is a coverage gap rather than a code defect: **no phase in this milestone produced a SECURITY.md**, in a milestone whose central act was publishing to a public registry with a credentialed CI workflow.

## The One Scheduled Action

`npm install @falkensmage/sigil-spinner` today gets version `1.0.0` and no element. The repo has moved past what the registry serves.

This is not drift that happened to someone — it is the boundary Phase 7 drew on purpose. D-98 reads: *"this phase does not publish and `version` stays `1.0.0`. ... At phase close, `npm install @falkensmage/sigil-spinner` still resolves to `1.0.0` and gets no element — publishing `1.1.0` through the proven release workflow is a milestone-close action."*

The release workflow that would do it is proven: it published `1.0.0` with a verified Sigstore attestation, ran its six gates in order, and has exactly one successful run on record. The version bump plus a `workflow_dispatch` is the whole remaining action.

Two things were worth deciding before dispatching it. **Both are now resolved** — recorded here with their outcomes rather than rewritten, since the reasoning is the useful part:

1. ~~**Security first or publish first.**~~ Security went first. `/gsd-secure-phase 6` ran on 2026-08-09 while the surface was still `1.0.0`, and found two real defects in the release workflow rather than confirming a clean bill.
2. ~~**Phase 6's WR-01 touches the promote path.**~~ Closed as T-06-17. The promote step now asserts the manifest version equals the registry's current `next` and refuses otherwise — proven against the exact stale-`main` scenario (manifest `1.0.0` vs next `1.1.0` → blocked). The 1.0.0 promote was a no-op because npm auto-assigned `latest` on first publish; the 1.1.0 promote is the first real one, and it now runs guarded.

One forward risk surfaced by that pass is worth carrying here, because it changes what "publish 1.1.0" means: **the auto-`latest` quirk does not recur.** The registry seeds `latest` only when there is none. So `1.1.0` published with `--tag next` leaves `latest` at `1.0.0`, and the element stays invisible to default consumers until the promote runs. The publish is two rungs, not one.
