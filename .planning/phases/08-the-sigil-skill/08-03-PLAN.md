<objective>
Give the skill the operational depth a session needs to ship a working page, bound it honestly to what the published package actually exposes, and write down the instrument for the two success criteria that have no automated substitute.

Purpose: the skill's job is to make a cold session behave like a session that has read the README — not to become a second interface to the tool. That means carrying the handful of facts a session would otherwise learn by shipping a broken page, pointing at the README for everything else, and being explicit about the one thing the local tree has that the registry does not. The verification instrument is a deliverable with the same standing as the skill itself: Phase 7 made exactly this argument for its example page and it held.

Output: the embedding checklist, the on-demand depth pointers, the recorded published-surface boundary, and `skill/VERIFY.md`.

Decisions implemented by this plan: D-105 (mechanics plus judgment inline, everything exhaustive read on demand), D-106 (the five-item operational embedding checklist), D-116 (document only what the published package resolves to, verified against the live registry at authoring time), D-118 (the cold-session check written down as a repeatable fixed-prompt procedure), and the procedural half of D-117 (the live registry check, discharged in 08-04).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public npm registry → authored documentation | What the skill claims the package exposes is only true if the registry is queried at authoring time; a stale assumption ships broken instructions to every future session. |
| skill body → the drift guard's parser | Growing the body can change what the guard's row regex extracts, turning a documentation edit into a false red or, worse, a false green. |
| verification procedure → the human running it | A procedure with an unstated precondition produces a false negative that reads as a real defect. |
