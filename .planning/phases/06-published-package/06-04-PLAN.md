<objective>
Take the last rung: make `1.0.0` the version a bare `npm install @falkensmage/sigil-spinner`
resolves to.

This is the smallest command in the phase and the one with the widest blast radius. The
publish in 06-03 put a real artifact on the registry that only someone asking for `@next`
could reach. This plan hands it to everyone by default — every future consumer, every Claude
Code session that installs the package without naming a tag, and Phases 7 and 8, which both
depend on the published package.

`npm dist-tag add` is a pure registry metadata operation. It does not republish, does not
create a version, and does not regenerate or invalidate the attestation already attached to
`1.0.0`. That is exactly what makes the ladder's step 4/5 split work: the artifact everyone
gets is byte-identical to the artifact that was reviewed under `@next`, and this plan proves
that rather than assuming it.

Purpose: PKG-01's final rung (D-75).
Output: `latest` pointing at `1.0.0`, the attestation intact, and the ladder's evidence closed.
</objective>

  <context>
This is the checkpoint the ladder's step 4/5 split exists to create. `1.0.0` has been on the
registry under `@next` since plan 06-03, which means it has been reachable and inspectable but
has not been in anyone's default install path.

What 06-03 verified live, and what is recorded in `06-RELEASE-LOG.md`:

- a clean install from the registry resolves, with zero transitive runtime dependencies;
- `import { generateSigil }` works and `npx sigil-spinner ... --planet saturn` writes a real
  sigil, neither needing additional configuration;
- `npm audit signatures` reports a verified provenance attestation, and the provenance panel
  renders on the npm page naming `mstine/sigil-spinner`;
- the npm page shows MIT with the `LICENSE` in the tarball, the author, a repository link that
  resolves, and public access.

Before answering, this is the moment to actually look at the npm package page one more time —
the README rendered there is what a first-time consumer reads, and the v1.0 lesson is that both
real v1.0 defects passed a fully green suite and were caught by a human looking at output.

**What the promote costs.** `latest` is the default resolution for every bare
`npm install @falkensmage/sigil-spinner`, and Phases 7 and 8 both consume the published
package. Unlike the publish in 06-03, this one is not strictly irreversible — `latest` can be
re-pointed at another version later — but it is not free either: anyone who installs between
the promote and a hypothetical correction has `1.0.0` on disk, and a repointed `latest` does
not reach them. Rated `costly`, not `one-way`.

**What holding costs.** Nothing on the registry. `1.0.0` stays live under `@next` and the
promote can run whenever. Phases 7 and 8 stay blocked on a package that is published but not
default-resolvable.
  </context>

Before promoting, capture the current registry state so the "nothing changed" assertion has a
baseline: record `npm view @falkensmage/sigil-spinner@1.0.0 dist.shasum` and

Dispatch the promote through the workflow rather than running `npm dist-tag add` from this
machine: `gh workflow run release.yml --repo mstine/sigil-spinner --ref main -f mode=promote`.
Keeping the promotion in the same workflow is what keeps the npm credential in exactly one
place (D-76); a local `dist-tag add` would require a second credential path on this machine
for no benefit. Do not pass `dist_tag` — the promote step ignores it and reads the version
from `package.json` via `npm pkg get version`, which is what keeps a caller-supplied string
out of a shell command in a job holding the publish token.

Watch the run with `gh run watch` and confirm it concludes `success`. The promote run does not
execute the six D-77 gate steps — they are conditioned on `mode == 'publish'` — so a short run
is expected and correct, not a sign the gates were skipped.

   remove `next` — they coexist on one version. This is the assertion that distinguishes a
