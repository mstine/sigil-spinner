## The decision the constraints demanded: coerce for `null`, reject for a wrong-typed bag

The task constraint says reject unless the codebase's own validation style shows coercion is what it does for analogous inputs. It does, and the discriminator is visible in the code:

- **Required slot given `null` → reject.** `statement` and `planet` throw `E_MISSING_STATEMENT`/`E_MISSING_PLANET`. There is no legal "absent" state for them, so `null` can only be an error.
- **Optional slot given `null` → treat as absent.** This is D-49/D-50, applied to `idPrefix`, and the codebase committed to it hard enough to *deliberately invert a previously-rejecting test* to get there (`test/cli/cli.test.js:609-619`: "This assertion was inverted deliberately (D-49a): it used to assert that a null idPrefix throws `E_INVALID_OPTION`"). The stated motivation — `working.render` round-trips as a legal `GenerateOptions` object — is the same motivation that makes `opts || null` a reasonable caller idiom for the bag itself.

`options` is an optional slot: `@param {GenerateOptions} [options]`, defaulted to `{}`, and `generateSigil(s, p)` / `generateSigil(s, p, {})` are legal and identical today. So under this codebase's own rule, `null` for `options` means absent. **Chosen: coerce `null`/`undefined` to absent.**

The reject half of the same rule still applies to a bag that is *present and structurally wrong*: a primitive or a function is not a property bag under any reading, so it throws the existing, documented `E_INVALID_OPTION` — no new code invented.

**Boundary, decided rather than left implicit:** an array passes the object check and resolves to all-defaults. That is deliberate and consistent with D-47's ignore-unknown-keys forward-compatibility rule (an array is an object carrying no known option keys, exactly like `{}`). A function is rejected, because `typeof` distinguishes it and it is not a property bag. State this in the doc comment so the asymmetry is a recorded choice.
